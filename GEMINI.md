# GEMINI.md — дополнения для агента Gemini

Главные правила — `AGENTS.md` (Gemini читает его через строку выше). Здесь только то, чего там нет: договорённости руководителя с Gemini и пометки для проверки его работы другим агентом. При расхождении прав `AGENTS.md`.

## 1. Начало сессии
`AGENTS.md` → `PROGRESS.md` («Текущий фокус») → документы задачи по `AGENTS.md` §6.1; среда в Linux-машине — `docs/DEV-ENV.md` §2. Файлы в ответах руководителю — кликабельными ссылками `[имя](file:///абсолютный/путь)`.

## 2. Договорённости с руководителем
- Не трогать `remaster/secrets`.
- Рабочий сервер пользователя (`server/ModernUO/Distribution`: `Saves`, `Configuration`) не менять и не запускать: проверки с сервером — только на временных копиях, как в `tools/check/*.sh`.
- Unity не запускать: компиляцию проверяет руководитель (`tools/check/all.sh --unity`).
- `docs/CONTROLS.md` и другие утверждённые решения менять только по слову руководителя; новое решение — ADR (`AGENTS.md` §6.7). «Решение пользователя» записывать, только если руководитель прямо его подтвердил.
- Историю git не переписывать: никаких `rebase`, `reset`, `--force`, `--amend` для чужих коммитов.

## 3. Пометки для ревью
Работу Gemini проверяет другой агент, поэтому:
- Автор каждого коммита в обоих репозиториях — `Gemini`: `git -c user.name="Gemini" -c user.email=noreply@example.com commit …` (остальные агенты подписываются `The Verge`, `docs/DEV-ENV.md` §2). Коммит без этой подписи ревью может пропустить.
- В конце тела коммита две строки: `Agent: Gemini` и `Для проверки: <что проверить и где сомнения>`.
- Сомнительное место в коде — комментарий `// REVIEW(Gemini): <вопрос>`, только при настоящей причине.
- Строка хроники в `PROGRESS.md` — обычным пунктом списка: `- **дата** — [Gemini] что сделано, коммиты, что НЕ проверено`.
- Правка сервера — строка в `docs/server-patches.md` с пометкой `(Gemini)`.
- Изменённый или удалённый тест — имя и причина в теле коммита и в ответе руководителю (`AGENTS.md` §6.4).
