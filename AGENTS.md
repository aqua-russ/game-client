## 1. Проект в пяти фактах

1. **The Verge** — 2D-изометрическая онлайн-игра с механиками Ultima Online. Ориентир — русские pre-AoS шарды (The Abyss): эра Renaissance, одна Фелукка. Приоритет сейчас — механики; графика — Стадия 9.
2. **Сервер** — форк ModernUO (.NET 10, C#), `../../server/ModernUO`, `127.0.0.1:2593`. Единственный источник истины.
3. **Клиент** — Unity 6 (`6000.6.8f1`), этот репозиторий. Клиент = ввод + отображение + предсказание шага. Больше ничего.
4. **Связь** — только бинарный протокол UO по TCP. Общих DLL с сервером нет. Код ModernUO (GPL-3.0) в клиент **не копируется** — только читается как справочник.
5. **Логика клиента пишется так, чтобы работать без Unity**: те же сборки Core/Network запускаются в headless-боте и в тестах `dotnet test`.

## 2. Архитектура клиента

### 2.1. Сборки и зависимости

```text
             ┌───────────────┐
             │   Bootstrap   │  composition root: единственный, кто знает все сборки
             └──┬─────┬────┬─┘
                │     │    │
   ┌────────────▼┐  ┌─▼────┴─────────┐
   │Presentation │  │    Network     │  (чистый C#)
   │  (Unity)    │  └──────┬─────────┘
   └──────┬──────┘         │
          └───────┬────────┘
               ┌──▼───┐
               │ Core │  чистый C#, ни от кого не зависит
               └──────┘
```

| Сборка (`.asmdef`) | Можно ссылаться на | `noEngineReferences` | Отвечает за |
|---|---|---|---|
| `TheVerge.Core` | — | **true** | примитивы, состояние мира, правила предсказания, команды игрока, порты (интерфейсы) |
| `TheVerge.Network` | Core | **true** | сокет, нарезка, Huffman, чтение/запись пакетов, обработчики пакетов |
| `TheVerge.Presentation` | Core, Unity-пакеты | false | ввод, камера, рендер мира, UI, звук |
| `TheVerge.Bootstrap` | Core, Network, Presentation | false | сборка объектов, запуск, конфиг подключения |
| `TheVerge.Editor` | всё | false (Editor only) | утилиты редактора |

- **Presentation не ссылается на Network.** UI не знает, что существуют пакеты. Нарушение = ошибка компиляции (так и задумано).
- Зависимости правятся **только** через `.asmdef` и только с ADR.
- Новая сборка — только с ADR и согласованием.

Правило размещения: **сначала слой (сборка), внутри — домен.** Домены одинаково называются во всех слоях:
`Core/Combat` ↔ `Network/Packets/Combat` ↔ `Presentation/UI/Combat`. Новый домен — новая папка в каждом нужном слое, не новый «модуль фичи» со своими правилами.

### 2.3. Поток данных (один путь, без вариантов)

**Входящее:**
1. `TcpConnection` (фоновый поток): читает байты → Huffman → `PacketFramer` режет по `PacketTable` → кладёт целый пакет (буфер из пула) в очередь. **Больше фоновый поток ничего не делает.**
2. `GameClient.Tick(now)` (главный поток Unity или цикл бота): забирает пакеты из очереди **с бюджетом времени на кадр** и вызывает обработчик по id.
3. `*Handler` читает поля через `PacketReader` и вызывает метод **доменного состояния** в Core (`world.UpdateMobile(...)`).
4. Состояние меняется и поднимает **типизированное C#-событие** (`MobileUpdated`).
5. Presenter, подписанный на событие, обновляет View.

**Исходящее:**
1. View передаёт ввод в Presenter → Presenter вызывает команду из `Core/Commands` (`commands.Movement.Step(dir, run)`).
2. Команда проверяет локальные ограничения (throttle, очередь шагов, sequence) и пишет пакет через `IPacketSink` (реализован в Network).

Следствия:
- Нет `IMainThreadDispatcher` для сети и нет `Task.Run` в логике: всё состояние меняется в одном потоке, как на сервере.
- Нет глобального EventBus. Кто на что подписан — видно по коду. Если двум доменам нужна реакция друг на друга — связывай явно в `GameClient`.
- Нет «фасадов-адаптеров» на десятки методов. Состояние — в доменных хранилищах, действия — в доменных командах.

### 2.4. Авторитет сервера и предсказание

| Что | Клиент предсказывает? | Как |
|---|---|---|
| Шаг персонажа | **да** | очередь шагов, откат по `0x21`, подтверждение по `0x22` |
| Поворот тела к мыши (3б) | да, визуально | сервер проверяет направление при ударе/блоке |
| Урон, HP, смерть, крафт, вес, золото | **нет** | только по пакетам сервера |
| Перенос предмета (`0x07`→`0x08`) | **нет** | ждём ответа, при `0x27` возвращаем |
| Открытие окон, торговля, гампы | **нет** | только по пакету сервера |

Нужна механика, которой нет в протоколе UO (например, «скрафти рецепт N»)? **Сначала сервер.** Клиент не изобретает команды без серверного пакета — в ModernUO крафт, банк, вендоры работают через гампы и стандартные пакеты.

### 2.5. Наши механики и расширения протокола

1. Механика реализуется на сервере (см. §5), клиент только отображает и отправляет ввод.
2. Новый/изменённый пакет → запись в `docs/protocol/extensions.md` (id, поля, направление, версия) **до** кода.
3. Расширение включается флагом при входе в мир. **С флагом выключенным клиент работает с ванильным ModernUO.**

## 3. Код-стайл

### 3.1. Язык

- **C# 9** (предел компилятора Unity 6). Нельзя: file-scoped namespace, `global using`, `record struct`, required members. `dotnet/*.csproj` держат `<LangVersion>9.0</LangVersion>` и `netstandard2.1`, чтобы ошибка ловилась без Unity.
- `#nullable enable` в Core и Network.
- Классы по умолчанию `sealed`. Наследование — только осознанно.
- DTO и события — `readonly struct`. Изменяемое состояние — классы в доменах Core.
- Время — только через `IClock` (мс, `long`). Никаких `DateTime.Now` и `UnityEngine.Time` в Core.

### 3.2. Размеры

| Метрика | Цель | Жёсткий предел | Если превышено |
|---|---|---|---|
| Строк в файле | ≤ 200 | 300 | выдели класс |
| Типов в файле | 1 верхнеуровневый | 1 (+ private nested) | разнеси по файлам |
| Строк в методе | ≤ 30 | 50 | выдели метод |
| Вложенность `if/for/switch` | ≤ 2 | 3 | guard clause, выдели метод |
| Параметров у метода | ≤ 4 | 6 | struct параметров |
| Зависимостей в конструкторе | ≤ 5 | 7 | класс делает слишком много |
| Членов в интерфейсе | ≤ 7 | 10 | раздели по ролям |

Исключения (помечаются в первой строке файла комментарием `// size-exempt: <причина>`): сгенерированный код `*.g.cs`, таблицы данных (Huffman, длины пакетов, каталоги), тестовые наборы данных.

### 3.3. Именование

- Файл = имя типа. `namespace` = путь папки (`TheVerge.Network.Packets.Combat`).
- `PascalCase` — типы, методы, свойства, константы. `_camelCase` — приватные поля. `camelCase` — параметры и локальные.
- Интерфейсы `I…`. Булевы `Is/Has/Can…`. Асинхронные методы `…Async`.
- События — прошедшее время: `MobileMoved`, `ItemRemoved`. Команды — повелительное: `Step`, `Attack`, `UseItem`.
- Входящий пакет: `<Смысл>Handler` + `public const byte PacketId = 0x1B;`. Исходящий: `<Смысл>Packet` со статическим `Write(ref PacketWriter, …)`. Подкоманды `0xBF`: `<Смысл>Handler` + `SubCommand`.
- Имя по смыслу UO/ModernUO, а не по нашей фантазии: `LoginConfirmHandler`, а не `PlayerSpawnHandler`.

### 3.4. Комментарии

- Комментарий объясняет **почему**: особенность протокола, ловушку версии, связь значений. Не пересказывает код и не описывает историю правок.
- У каждого `*Handler`/`*Packet`: `/// 0x1B Login Confirm. Сервер: Projects/Server/Network/Packets/Outgoing….cs` — откуда сверяли.

### 3.5. Протокол

- Все многобайтовые числа — **big-endian** через `BinaryPrimitives` внутри `PacketReader/Writer`. Нигде больше байты руками не собираются.
- Длины и id пакетов — только из `PacketTable.g.cs`. Магические числа протокола в коде — запрещены.
- Любые длины и счётчики из пакета проверяются на разумный предел до выделения памяти.
- Ошибка разбора пакета известной длины: лог + пропуск пакета. Неизвестный id или поломанная нарезка: **контролируемый дисконнект с дампом**, никогда не зависание и не тихое продолжение.
- Конкретные значения (версия клиента, скорости шагов, правила sequence, троттлинг) — в `docs/TARGET.md` и одном классе `ServerLimits`. **В коде и в этом файле их не дублировать.**

### 3.6. Подписки, ресурсы, асинхронность

- Каждая подписка `+=` имеет зеркальную `-=` в `Dispose()`/`OnDisable()`. Presenter реализует `IDisposable`.
- Всё, что открывает сокет, поток, таймер — `IDisposable` и принимает `CancellationToken`.
- `async void` — запрещён (кроме обработчиков Unity-событий, и там — с try/catch).
- Ошибки не глотаются: `catch` либо логирует с контекстом, либо пробрасывает.

## 4. Правила Unity (только Presentation, Bootstrap, Editor)

### 4.1. Общее
- Ввод — только Input System. `UnityEngine.Input` запрещён.
- Запрещены в рантайме: `GameObject.Find`, `Transform.Find`, `FindObjectOfType/FindAnyObjectByType`, `SendMessage`, синглтоны `static Instance`.
- В `Update/LateUpdate/FixedUpdate`: без `GetComponent`, LINQ, `new` ссылочных типов, конкатенации строк.
- Сущности мира, эффекты, ячейки списков — через `ObjectPool<T>`; возврат в пул по удалению сущности (`0x1D`).
- `[SerializeField] private` для полей инспектора. При переименовании — `[FormerlySerializedAs]`.
- Сцена одна — `Bootstrap`. Всё связывается кодом в `Bootstrap`. Руками в сцене — минимум.

### 4.2. Ассеты
- Каждый файл в `Assets/` имеет `.meta`. Перемещать — **вместе с `.meta`**. GUID не перегенерировать, `.meta` не удалять.
- `.unity` и `.prefab` руками в YAML не править, кроме тривиальных замен. Нужен новый ассет — генерируй его Editor-скриптом в `Editor/` и запускай через batchmode.

### 4.3. UI
- Окна и HUD не собираются в рантайме из C# (`new GameObject` + `AddComponent<RectTransform>` + пиксельные смещения).
- Разметка — текстовыми файлами **UI Toolkit (UXML + USS)** в `Assets/TheVerge/UI/<Domain>/`; C#-класс View только находит элементы по имени и привязывает данные. Решение принято: [ADR 0007](docs/adr/0007-ui-toolkit.md). Существующий uGUI прототипа — долг, новый UI на uGUI не пишем.
- Клик в мир сначала проверяет, не над UI ли курсор (единый `PointerOverUiGuard`).
- Серверные гампы рисуются **универсальным рендерером** по их разметке (Стадия 6). Для отдельных гампов можно зарегистрировать «скин» по TypeID — он обязан отправлять тот же `0xB1`, что и универсальный.
- `Esc` работает стеком: каст → верхнее окно → таргет.

### 4.4. Графика (до Стадии 9)
- Отладочный рендер: цветные тайлы и маркеры. Не тратить время на спрайты, атласы, анимации, освещение.
- Порядок отрисовки делается по правилам UO (X+Y, Z, приоритет слоя), а не сортировкой Unity по оси. Решение — на Стадии 9 через ADR.

## 5. Правила для сервера ModernUO

1. Перед правкой сервера прочитай `../../server/ModernUO/CLAUDE.md` — его правила (однопоточность, сериализация, `PooledRefList`, фигурные скобки, tick-арифметика и т.д.) **обязательны**.
2. Наш контент — в `Projects/UOContent/Custom/TheVerge/` или partial-файлами `*.TheVerge.cs` рядом с оригиналом. Оригинальные файлы `UOContent` меняй минимально. Любая правка сервера — строка в `docs/server-patches.md`.
   Песочница `Custom/MinocSandboxInitializer.cs` — долг: не расширять, новый код клиента на неё не опирается (ADR 0004).
3. Движок `Projects/Server/` — **только с явного разрешения пользователя.** Каждая правка: комментарий `// THE VERGE: <причина>` и строка в `docs/server-patches.md` (файл, что, зачем). Это наш долг при обновлении ModernUO.
4. Эра (`Core.AOS` и т.п.) — из `docs/TARGET.md`, не угадывать.
5. Ничего не отправлять в апстрим ModernUO и не подтягивать оттуда без согласования (их Workflow Rules).
6. Сервер собирается: `dotnet build` из корня ModernUO. Сломанная сборка сервера = задача не готова.

## 6. Порядок работы над задачей

1. **Контекст.** `PROGRESS.md` (текущий фокус), задача в `docs/PLAN.md`, `docs/TARGET.md`, нужные строки `packets.csv`, `CONTROLS.md` если задача про ввод.
2. **Уточнение.** Если по задаче нет правила в документах или есть противоречие — спроси. Не начинай с допущений.
3. **Нарезка.** Одна задача = один вертикальный срез одной стадии. Большая задача → предложи разбиение. Ориентир — diff до ~400 строк без учёта тестов и сгенерированного.
4. **Снизу вверх:**
   1. строка в `packets.csv` (если новый пакет) → перегенерировать таблицу;
   2. тест на байтах из `golden/` → `*Handler`/`*Packet`;
   3. доменное состояние/команда в Core + тест;
   4. Presenter + View;
   5. сценарий бота, если это критерий стадии.
5. **Границы.** Меняй только файлы своей задачи. Публичные сигнатуры Core меняешь — найди и обнови всех потребителей в той же задаче.
6. **Проверка** (§7).
7. **Документы.** `PROGRESS.md` — статус задачи и 1–3 строки в хронику. Новое решение — ADR. Новый пакет-расширение — `extensions.md`. Правка движка — `server-patches.md`.
8. **Ответ пользователю** (§9).

### Остановись и спроси, если:
- нужно изменить зависимости сборок, добавить пакет в `manifest.json` или NuGet;
- нужно править `Projects/Server/` или протокол;
- поведение по документам неоднозначно или противоречит серверу;
- тест или эталонный лог расходится с ожиданием, и непонятно, кто прав;
- задача требует нарушить правило из этого файла.

## 9. Ответ пользователю

Пользователь — руководитель проекта. Код в чат не выводится, если пользователь сам не попросил. Технический жаргон — по минимуму.
Ответ состоит из пунктов:
1. **Что сделано** — 1–3 предложения: какая возможность появилась или исправлена. Если менялся сервер — одной фразой.
2. **Что нажать в Unity** — по шагам; в идеале «Откройте сцену `Bootstrap` и нажмите Play».
3. **Как проверить** — сценарий проверки глазами в игре (или команда бота).
4. **Вопросы и риски** — только если есть: что требует решения пользователя.

## 10. Git

- Не коммитить: `Library/`, `Temp/`, `Logs/`, `UserSettings/`, `obj/`, `bin/`, `.DS_Store`, архивы.
- Коммит — только по просьбе пользователя. Формат: `[Слой/Домен] Что сделано` (`[Network/Movement] Обработка 0x21 Move Reject`).
- Одна задача — один коммит. Не смешивать рефакторинг и новую функциональность.
