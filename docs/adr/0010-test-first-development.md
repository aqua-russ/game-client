# ADR 0010. Разработка через тесты: сначала тест, потом код

- **Статус:** принято, 11 ноября 2026 (решение пользователя)

## Контекст
1. Логику клиента (Core, Network, Data) используют два клиента — Unity и headless-бот: обе программы собирают одни и те же исходники. Тест в `dotnet/TheVerge.Tests` проверяет логику сразу для обоих.
2. Агент в облаке не может запустить Unity. Тест — единственный способ для агента самому доказать, что логика работает, ещё до проверки пользователем на Mac.
3. Пользователь не читает код. Ему проще подтвердить список ожидаемого поведения простыми словами, чем проверять сам код.
4. Тест, написанный после кода, часто повторяет ошибку кода: проверяет то, что код делает, а не то, что делает сервер.
5. `AGENTS.md` уже требовал тест к каждой задаче (§6, §7), но не порядок «сначала тест».
6. ИИ-агент может «получить зелёную проверку» нечестно: поправить ожидание под ошибочный код, ослабить проверку или написать код, который узнаёт тестовые данные. Такой тест обманывает пользователя, который сам код не читает и судит о готовности по проверкам (дополнено 11 ноября 2026).

## Решение
1. **Цикл «красный → зелёный → чистка».** Сначала тест. Запуск: тест падает на проверке ожидаемого поведения, а не из-за ошибки в самом тесте (если нужного типа ещё нет — сначала пустая заготовка, чтобы тест собрался). Затем минимальный код, чтобы тест прошёл. Затем чистка под `AGENTS.md` §3 при зелёных тестах.
2. **Где обязательно:** всё новое и изменённое поведение в Core, Network и Data. Ошибка — сначала тест, который её воспроизводит, потом исправление. Тесты лежат в `dotnet/TheVerge.Tests`, папки повторяют слой и домен (`Network/Compression/…`).
3. **Откуда ожидания:** из источников правды `AGENTS.md` §0 — исходник сервера ModernUO (путь — в комментарии теста), эталонные логи `golden/`, `docs/TARGET.md` и `ServerLimits`. Не из памяти, не из чужих описаний протокола и не из текущего кода клиента. Тест расходится с сервером — прав сервер; непонятно, кто прав, — остановиться и спросить (`AGENTS.md` §6).
4. **Список проверок до кода.** План задачи, который пользователь подтверждает до начала работы, содержит список проверок простыми словами, например: «шаг в стену — сервер отказывает, персонаж остаётся на месте». По этому списку пишутся тесты.
5. **Код прототипа.** Перед изменением старого файла — тест, фиксирующий его текущее поведение; после рефакторинга этот тест проходит без изменений. Если текущее поведение расходится с сервером, тест пишется на поведение сервера, а исправление называется в ответе пользователю. Удаляемые файлы тестами не покрываются.
6. **Unity (Presentation, Bootstrap, Editor):** «сначала тест» не обязателен — эти сборки проверяются компиляцией Unity и шагами «Как проверить» (`AGENTS.md` §9). Поэтому в них держится минимум логики: всё, что можно проверить тестом, живёт в Core. Тесты внутри Unity (Unity Test Framework) — отдельным решением, если понадобятся.
7. **Без теста:** документы, настройки, разметка UI. Сгенерированный код (`*.g.cs`) напрямую не тестируется — тестируется результат генерации (например, длина каждого пакета совпадает с `packets.csv`). Скрипты проверки `tools/check` проверяются прогоном с намеренно внесёнными нарушениями.
8. **Коммит:** тест и код — в одном коммите задачи. Состояние с падающим тестом не коммитится.
9. **Тест и код не подгоняются друг под друга** (дополнено 11 ноября 2026 по решению пользователя). Цель тестов — код хорошего качества с минимумом ошибок, а не зелёная проверка.
   - Упал тест — исправляется код, а не тест. Нельзя менять ожидание под результат кода, ослаблять проверку (допуск, «не пусто» вместо точного значения), пропускать, удалять или переписывать падающий тест.
   - Нельзя писать код под тест: подставлять ожидаемое значение, отдельная ветка для тестовых данных или тестовой среды, заглушенная ошибка (пустой `catch`, значение по умолчанию вместо ошибки).
   - Нельзя «зеленить» проверки базовыми линиями или отключением правил без согласия пользователя (ADR 0009).
   - Тест меняется, только если неверен он сам — его ожидание расходится с источником правды (п. 3); ссылка на источник — в коммите, причина — в ответе пользователю. Тест удаляется только вместе с кодом, который удаляется по решению пользователя, и это тоже называется в ответе.
   - Очевидная ошибка в коде, в том числе в старом, не закрепляется тестом как «текущее поведение» (п. 5): сначала тест, который её показывает, потом исправление.
   - Не ясно, кто прав, тест или код, — агент останавливается и спрашивает (`AGENTS.md` §6).

## Последствия
- У каждого поведения логики есть тест, который сначала падал; `tools/check/all.sh` гоняет их все.
- Задача становится немного длиннее, зато ошибки ловятся в облаке, до проверки на Mac.
- Если в среде агента закрыт NuGet, агент гоняет тесты временной заменой NUnit вне репозитория и прямо пишет об этом в ответе; окончательная проверка — `tools/check/all.sh` на Mac. Как проверить доступ и настроить среду — `docs/DEV-ENV.md` §2 (уточнено 11 ноября 2026: доступ к NuGet открыт).
- Аудит прототипа (задача 0.9) идёт по пункту 5: сначала тест на текущее поведение файла, потом рефакторинг.
- Зелёная проверка значит одно: код делает то, что делает сервер. Каждое изменение или удаление существующего теста видно пользователю в ответе (п. 9).
