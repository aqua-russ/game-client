# Unity-клиент для ModernUO: аудит и план реализации

*Подготовлено Claude · 10 ноября 2026*

Цель проекта: клиент на Unity для сервера ModernUO (аналог Ultima Online). Графика пока не важна, приоритет — игровые механики и максимальный перенос механик, реализованных на сервере.

## 2. Стадия 0: чеклист (примерно неделя)

1. **Репозиторий.** `Core` (netstandard2.1, без ссылок на Unity), `Tests`, `Bot` (консоль) и `UnityClient`, куда Core подключается через asmdef или dll. *Готово:* `dotnet test` зелёный, Bot запускается, Unity видит Core.
2. **Стенд.** Соберите ModernUO из исходников, укажите путь к UO-данным в `dataDirectories` файла `modernuo.json` и создайте два аккаунта: GM и обычный. *Готово:* ClassicUO заходит на ваш сервер и ходит по миру.
3. **Целевая версия.** Выберите клиент и эру. Версия клиента задаётся в `clientData.clientVersion` файла `modernuo.json`, эра — в `expansion.json`. Проверка клиента (`clientVerification`) включена по умолчанию: подходящие типы клиента Classic и SA, неподходящих кикают через 20 секунд. Значит, Bot и Unity-клиент должны честно представляться. *Готово:* `docs/TARGET.md` с версией, типом клиента, настройками проверки и режимом шифрования (network.encryptionMode = None).
4. **Матрица пакетов (главная задача).** CSV со столбцами: id, sub, направление, длина (фиксированная или динамическая), условие по версии, использует ли сервер, приоритет P0–P3, стадия. Входящие пакеты берите из `Projects/Server/Network/PacketHandlers.cs`. Исходящие ищите в extension-методах NetState: класс Packet заменён ими. Основной источник — справочник пакетов ModernUO (modernuo.com/packets.html): размеры, поля и путь к исходнику каждого пакета, так что большую часть матрицы можно собрать оттуда. Он же закрывает вопрос по сомнительным номерам: 0xBF sub 0x24 и 0x12 сервер не использует, 0xF0/0xFE выключены по умолчанию, чат 0xB3/0xB5 есть, но выключен по умолчанию. *Готово:* у каждой строки исходного документа есть статус «нужно», «не используется» или «отложено».
5. **Один источник правды.** Из CSV генерируйте `PacketTable.cs` (длины и имена). Тест на каждый id: длина и направление совпадают с CSV. Неизвестный id приводит к контролируемому дисконнекту с дампом, а не к зависанию. *Готово:* тесты зелёные.
6. **Эталонные логи.** Прогоните через ClassicUO 8 сценариев: вход, 20 шагов, речь, drag предмета, открытие контейнера, гамп, прицел, смерть. Для логов у сервера есть `netstate.packetLoggingPath`. Если его не хватит, поставьте TCP-прокси. Сохраните результат в `golden/`. *Готово:* 8 логов, позже Bot должен слать те же пакеты.
7. **Лимиты сервера.** Выпишите задержки шага (бег пешком 200 мс, верхом 100 мс) и троттлинг пакетов 0x03, 0x12, 0x75 и 0xAD из `throttles.json`. Для игроков сервер отбрасывает пакеты, пришедшие чаще этих задержек (для персонала лимиты не действуют), поэтому макросы и речь клиента обязаны в них укладываться. *Готово:* константы лежат в одном файле настроек клиента.
8. **Лицензии.** ModernUO выпущен под GPL 3.0: читайте его как справочник, но не копируйте код в клиент, иначе клиент придётся открывать под GPL. Для ClassicUO источники расходятся: README указывает BSD 4, а SignPath — 2-clause BSD. Откройте файл LICENSE и при порте сохраняйте уведомление. *Готово:* `docs/LICENSES.md` с решением «Core пишем заново, ClassicUO только справочник».

**Стадия закрыта,** когда есть матрица, TARGET.md и 8 эталонных логов, а ClassicUO стабильно работает на вашем стенде.

## 3. Стадия 1: сеть и логин в headless-режиме (1–1,5 недели)

Стадия 1 даёт бота, который проходит путь «логин → шард → персонаж → вход в мир → ожидание → выход» против реального ModernUO, без графики. Всё, что сервер шлёт после входа в мир (объекты, свет, сезон), клиент пока только режет на пакеты по длинам и логирует; разбор начинается на Стадии 2.

### Принципы

- Порядок и состав пакетов берём из эталонных логов Стадии 0, а не из памяти и не из этого документа.
- Core не зависит от Unity. Сеть работает в фоновом потоке, данные уходят в main thread через очередь.
- Каждая задача закрывается тестом.

### Задачи

1. **Чтение и запись пакетов.** `PacketReader` и `PacketWriter` на Span: big-endian, ASCII (фиксированной длины и с нулём в конце), UTF-16BE. *Тест:* запись, а затем чтение возвращает те же значения для каждого типа поля.
2. **Нарезка потока.** Буфер собирает пакеты из кусков TCP любого размера по `PacketTable` (фиксированная длина или 2 байта длины). Отдельно обработайте 0xBF и 0xD7: подкоманда идёт после длины. *Тест:* эталонный лог, поданный кусками по 1 байту и случайной длины, даёт одну и ту же последовательность пакетов.
3. **Huffman (только сервер→клиент).** Потоковый декодер, состояние битов сохраняется между чтениями. Таблицу берите как данные из ClassicUO (лицензия: Стадия 0, п. 8). Сжатие работает на игровом сокете, на логин-сокете его нет; по эталонному логу проверьте, с какого пакета оно начинается. *Тест:* сжатый поток из эталонного лога декодируется в те же пакеты при любой нарезке.
4. **Транспорт.** Интерфейс `IConnection` (Connect, Send, события приёма) и реализация на `Socket` в фоновом потоке. Очередь входящих для main thread, таймаут подключения, корректное закрытие. Интерфейс нужен, чтобы в тестах подставлять фейковый сервер.
5. **Логин-сервер: seed и авторизация.** Seed и версия клиента из `TARGET.md` (расширенный 0xEF или классический 4-байтовый, как в эталонном логе), затем 0x80 с логином и паролем.
6. **Список шардов и редирект.** Разбор 0xA8, выбор 0xA0, разбор 0x8C (адрес, порт, ключ). Порядок байт IP в 0xA8 — частая ловушка, сверяйте по логу.
7. **Игровой сокет.** Новое подключение, 4 байта ключа из 0x8C отправляются сырыми, затем 0x91; включить Huffman, логин-сокет закрыть.
8. **Список персонажей.** Разбор 0xB9 (флаги функций) и 0xA9 (слоты, персонажи, стартовые города, флаги). Формат городов зависит от версии клиента, сверяйте с логом. Выбор персонажа отправляется пакетом 0x5D.
9. **Вход в мир.** Разбор 0x1B (серийник, тело, координаты, направление) в `PlayerState`, затем 0x55. После входа клиент шлёт ровно те метаданные, что ClassicUO слал в эталонном логе (версия, язык, флаги клиента, дальность обзора, размер экрана).
10. **Keepalive и выход.** Пакет 0x73 по таймеру (интервал из эталонного лога), учёт эха и RTT. Выход через 0x01 и 0xD1, обработка разрыва со стороны сервера.
11. **Типизированные ошибки.** Таблица ниже; клиент никогда не зависает молча.
12. **Логгер и сравнитель.** Дамп в формате «время, направление, id, имя, hex». Утилита сравнивает исходящие пакеты бота с эталоном; изменчивые поля (ключи, время, счётчики) закрываются маской.
13. **Фейковый сервер для CI.** Проигрывает записанный сценарий входа, и бот проходит его без ModernUO.
14. **Устойчивость.** Лимит размера пакета, неизвестный id, обрезанные данные ведут к контролируемому дисконнекту с дампом, а не к зависанию.
15. **Bot.** Консольное приложение: хост, порт, логин, пароль, имя персонажа, сценарий `login-idle-logout`.
16. **Unity-оболочка.** Сцена без графики: поля логина, список шардов, список персонажей, строка статуса «в мире». Core вызывается из `Update()` с лимитом времени на разбор очереди.

### Реакция клиента на ошибки

| Событие | Реакция клиента |
| --- | --- |
| 0x82, отказ логина | Ошибка `LoginDenied` с кодом причины, соединение закрывается |
| 0x53, отказ входа персонажа | Ошибка `CharacterRejected` с кодом причины |
| Разрыв примерно через 20 с после входа без других причин | Ошибка `Disconnected` и подсказка в логе проверить `clientVerification` и версию из `TARGET.md` |
| Разрыв сокета в мире | Событие `Disconnected`, переподключение с нарастающей паузой |
| Таймаут подключения | Повтор с нарастающей паузой, затем ошибка |

### Критерии готовности

| Проверка | Порог |
| --- | --- |
| 100 входов подряд на реальном ModernUO | 0 сбоев |
| Ожидание в мире | 2 часа без разрыва |
| Выход | Нет ошибок на сервере, повторный вход сразу возможен |
| Неверный пароль, неверная версия клиента | Типизированная ошибка, без зависания |
| Сценарий «вход» против эталонного лога | Исходящие пакеты совпадают с учётом маски |
| Фаззинг случайными байтами | 1 млн входов без падения и зависания |
| Unity | Вход, список персонажей и статус «в мире» работают вручную |

### Риски

- Ошибка состояния Huffman проявляется только при некоторых размерах кусков TCP, поэтому тест нарезки из задач 2 и 3 обязателен.
- Адрес в 0x8C должен быть доступен клиенту: для локального стенда задайте serverListing.address = 127.0.0.1 (по умолчанию сервер определяет его через внешний сервис), а порт возьмите из `listeners` в `modernuo.json`.
- Интервал и поведение 0x73 берём из логов, а не из догадок.

## 4. Стадия 2: данные карты и состояние мира (1,5–2 недели)

Стадия 2 даёт клиенту ту же картину мира, что у сервера: земля, статика и multi из файлов данных плюс живые мобы и предметы из пакетов, и всё это сверяется с сервером автоматически. Графические файлы по-прежнему не нужны. Skills, cliloc, speech и containers.cfg подключаются на стадиях 4–5, когда они понадобятся.

### Принципы

- Формат файлов зависит от версии клиента (UOP или MUL, ширина флагов tiledata, размер записи multi). Нужно автоопределение с записью результата в лог и тесты на реальной папке данных вашей версии.
- Карту не читаем целиком: файл открываем через memory-mapped доступ, блоки 8×8 держим в LRU-кэше.
- Какие пакеты мира реализовать (0x78 или 0xD3, 0x1A или 0xF3), решают матрица Стадии 0 и эталонный лог «вход».
- Правда о мире — сервер. Для сверки пишем скрипты-дампы в ваш ModernUO, в клиент они не попадают.

### Задачи

1. **Пути и формат данных.** `UoDataPaths` (папка клиента) и автоопределение: карты в UOP или MUL, ширина флагов tiledata, формат multi (multi.mul или MultiCollection.uop). Результат пишется в лог при старте. *Тест:* загрузка на реальной папке, формат в логе совпадает с ожидаемым.
2. **Tiledata.** Земля и предметы: имя, высота, слой и флаги целиком в формате вашей версии (Impassable, Surface, Bridge, Wet, Roof, Foliage и остальные). *Тест:* для всех ID флаги и высота совпадают с дампом сервера.
3. **Карта.** Чтение блоков из UOP (хеширование имён HashLittle2) и из MUL. Размеры и ID карт берите из конфигурации сервера (проверьте, где ModernUO их задаёт). API: `GetLand(map, x, y)`. *Тест:* 10 000 случайных координат на каждой карте совпадают с дампом сервера.
4. **Статика.** staidxX и staticsX через тот же кэш, API `GetStatics(map, x, y)` с tileID, Z и hue. *Тест:* совпадение с дампом на тех же координатах.
5. **Dif-патчи (если нужны).** mapdif и stadif применяются, только если такие файлы есть в вашей папке данных и их использует сервер, иначе пункт пропускаем. Количество патчей по картам приходит в 0xBF 0x18. *Тест:* координаты внутри патчей совпадают с дампом.
6. **Multi.** Компоненты (itemID, смещения x/y/z, флаги) и габариты, API `GetMulti(id)`. *Тест:* 100 случайных multi совпадают с дампом по числу компонентов и габаритам.
7. **Модель мира.** `World` с реестром по Serial (мобы 0x00000001–0x3FFFFFFF, предметы 0x40000000–0x7FFFFFFF), классы `Mobile` и `Item`, связи «контейнер → содержимое» и «моб → надетое по слоям», каскадное удаление дочерних объектов. Неизвестный serial: 0x77 создаёт заглушку, 0x1D игнорируется, оба случая считаются в метрике.
8. **Пространственный индекс.** `QueryRange(map, x, y, radius)` по блокам. На нём будет стоять физика Стадии 3 (двери, мобы на клетке). *Тест:* случайные вставки, перемещения и удаления дают тот же результат, что полный перебор.
9. **Обработчики пакетов мира.** Разбираем 0x20 (0xD2), 0x78 (0xD3), 0x77, 0x1A (0xF3, включая тип Multi), 0x1D, 0x2E, 0xBF 0x08 (смена карты, мир очищается), 0xBF 0x18. Свет (0x4F, 0x4E), сезон (0xBC) и время (0x5B) только сохраняем в `Environment`. Остальное по-прежнему нарезается и логируется. Удаление по дальности включается настройкой как страховка к 0x1D. *Тест:* эталонный лог «вход» превращается в снимок мира, он совпадает с эталонным JSON.
10. **Мини-речь.** Только отправка текста через 0xAD (или 0x03, как в матрице) для GM-команд `[go`, `[add`, `[remove`. Журнал и приём речи остаются на Стадии 4. Лимиты из `throttles.json` соблюдаются.
11. **Серверные скрипты-дампы.** Команды вашего ModernUO: дамп земли, статики и multi по списку координат и дамп всего, что сервер считает видимым для вызывающего (serial, graphic, hue, x/y/z, контейнер). Результат — JSON-файлы для сверки.
12. **Parity-сценарии бота.** Сценарий `world-parity`: бот заходит GM-аккаунтом, телепортируется в 5 тестовых точек (город, подземелье, вода, дом, корабль), спавнит объекты и сверяет свой мир с дампом сервера. Отдельно проверяются удаление, перемещение NPC, телепорт и смена карты.
13. **Unity: отладочная карта.** Вид сверху вокруг персонажа: тайлы цветом по флагам (непроходимое, поверхность, вода, стена) и яркостью по Z, мобы кружками, предметы квадратами. Клик по клетке открывает инспектор со всеми объектами на ней: tileID, Z, флаги, имя. Инспектор — главный инструмент отладки Стадии 3.
14. **Устойчивость.** Фаззинг новых парсеров, обрезанные и противоречивые пакеты (контейнер без родителя, цикл вложенности) дают контролируемую ошибку, а не падение.

### Критерии готовности

| Проверка | Порог |
| --- | --- |
| Земля и статика против дампа сервера | 10 000 случайных координат на каждой карте, 100% совпадений |
| Tiledata | Флаги и высота совпадают для всех ID |
| Multi | 100 случайных multi совпадают |
| Мир бота против дампа сервера | Множества объектов совпадают по serial, graphic, hue, x/y/z и контейнеру в пределах View Range на 5 сценариях |
| Удаление, движение NPC, телепорт, смена карты | После обработки пакета мир сразу в корректном состоянии |
| Производительность (ориентир) | Блок карты из кэша быстрее 1 мс, поток 0x77 и 0x78 без аллокаций в установившемся режиме |
| Фаззинг новых парсеров | 1 млн входов без падений и зависаний |
| Unity | Карта вокруг персонажа рисуется, инспектор показывает объекты с Z и флагами |

### Риски

- Карты большие (одна Фелукка порядка 90 МБ в MUL), поэтому чтение целиком недопустимо: нужен memory-mapped доступ и кэш блоков.
- Версия клиента определяет форматы файлов и набор пакетов (0x78 или 0xD3, 0x1A или 0xF3). Расхождение с `TARGET.md` проявится только на реальных данных, поэтому тесты идут на вашей папке.
- Если сервер применяет dif-патчи, а клиент нет (или наоборот), расхождение будет точечным и его найдёт только parity-проверка на координатах внутри патчей.

## 5. Стадия 3: движение (2–3 недели)

Стадия 3 даёт боту и Unity-клиенту движение, совместимое с сервером: клиентская физика совпадает с серверной, шаги идут без откатов, а режим 3б добавляет направление тела, независимое от направления движения. Стадия делится на 3а (стандартное движение, сверяется с ClassicUO) и 3б (расширение по флагу в handshake). Проверки замаха и блока щитом относятся к Стадии 4.

### Принципы

- Сервер — арбитр. Клиент предсказывает шаг, а по отказу (0x21) откатывается на позицию сервера.
- Ввод отделён от протокола: `MoveIntent` (направление из WASD и флаг бега), `FacingIntent` (угол от мыши) и `IMovementProtocol` с двумя реализациями (3а и 3б). Таблица «экранное направление → направление UO» лежит в одном месте и покрыта тестом, поэтому смена камеры её не ломает.
- Тайминги берутся из настроек сервера: пешком бег 200 мс и ходьба 400 мс, верхом бег 100 мс и ходьба 200 мс, поворот на месте 0 мс (`movement.delay.*`). Клиентские константы лежат в `ClientConfig` и проверяются измерением.
- Код движения ModernUO не копируем (GPL): повторяем поведение и доказываем совпадение parity-тестами.

### 3а. Стандартное движение

1. **Ввод.** WASD по экрану: W вверх, D вправо, S вниз, A влево, диагонали из пар клавиш. В направлениях UO одиночные клавиши дают Up, Right, Down, Left, а пары дают North (W+D), East (D+S), South (S+A), West (A+W). Противоположные клавиши гасят друг друга. Бег: переключатель (CapsLock, запасной `R`) и Shift как инверсия режима, на экране индикатор. *Тест:* все 16 комбинаций дают ожидаемое направление и флаг бега.
2. **Физика `MovementCheck`.** По tiledata, земле, статике, динамическим предметам (двери и прочее непроходимое), multi (дома, лодки) и мобам на клетке считаем, можно ли шагнуть и какой будет Z. Учитываем высоту персонажа и высоту ступеньки (в ModernUO 16 и 2, сверьте по эталону), воду, мосты, лестницы и проверку соседних клеток при диагональном шаге. *Тест:* см. пункт 3.
3. **Серверный дамп движения.** Команда вашего ModernUO `[DumpMove x y z map dir` вызывает серверную проверку шага для игрока и для GM и пишет результат (можно ли и какой новый Z) в JSON. *Тест:* 100 000 случайных точек и направлений по всем картам, включая воду, лестницы, двери и дома, дают 100% совпадений.
4. **Состояние движения.** `PlayerMotion`: x, y, z, направление, бег, верховая езда (по предмету на слое 0x19), полёт (флаг моба) и очередь шагов с sequence.
5. **Очередь шагов.** Запрос 0x02: направление (бит 0x80 означает бег), sequence и fastwalk-ключ, всегда 0. Первый запрос после входа или отказа идёт с sequence 0, дальше 1–255 по кругу (сверьте по эталонному логу). Клиент применяет шаг сразу (предсказание) и держит его до подтверждения. Число неподтверждённых шагов настраивается (по умолчанию 3), потому что сервер сбрасывает очередь при глубине 10 (`movementThrottle.hardQueueLimit`). Темп отправки не быстрее задержки шага плюс небольшой кредит на джиттер. Если направление изменилось, сначала идёт запрос-поворот без движения, затем шаг: поворот на месте у сервера по умолчанию бесплатный.
6. **Ответы сервера.** 0x22 (подтверждение: sequence и известность) снимает шаг из очереди. 0x21 (отказ: sequence, x, y, направление, z) откатывает на позицию сервера, очищает очередь и сбрасывает sequence в 0. 0x97 и 0x20 (0xD2) принудительно меняют позицию (толчок, телепорт), 0xBF 0x08 (смена карты) сбрасывает очередь. При рассинхроне клиент шлёт запрос ресинхронизации 0x22 (3 байта, это не тот же пакет, что подтверждение). *Тест:* сервер по сценарию отвечает отказом, клиент откатывается и продолжает без зависаний.
7. **Скорости и ограничения.** Задержка выбирается по таблице «пешком или верхом × ходьба или бег», режим скорости приходит в 0xBF 0x26, полёт гаргульи сверьте по логам. Усталость и перегруз (`stamina.*`) могут давать отказы: клиент пишет в лог «отказ сервера», а не «ошибка клиента».
8. **Чужие мобы.** Позиции обновляются по 0x77 (и 0x78 или 0xD3). Сглаживание только в Unity-слое, в Core позиция дискретна.
9. **Отладка в Unity.** WASD, бег и Shift на отладочной карте Стадии 2, оверлей с очередью шагов, задержкой подтверждения, числом отказов, режимом скорости и Z.
10. **Сценарии бота.** `walk-route` (маршрут по точкам), `random-walk` (10 000 шагов), `door-test`, `stairs-test`. GM-аккаунт готовит сцену командами `[add` и `[go`.
11. **A* (необязательно).*\* Поиск пути по клику на карту, каждый шаг проверяется через `MovementCheck`. Делаем после закрытия критериев 3а.

### 3б. Независимое направление тела

12. **Флаг расширения.** В handshake клиент объявляет расширение Facing и его версию, сервер включает правила 3б только для такой сессии. ClassicUO и клиент без флага работают по-старому.
13. **Серверные правки.** (а) Для сессий с флагом шаг в новом направлении двигает сразу, без отдельного запроса-поворота. (б) У моба появляется `Facing`, отдельное от `Direction`. (в) Новый пакет «направление тела» от клиента: 16 секторов, лимит частоты, проверка скорости поворота. (г) Рассылка `Facing` соседним клиентам. Обработчик 0x02 лежит в `Projects/UOContent/Network/Packets/IncomingMovementPackets.cs`. Для нового пакета выберите id или подкоманду 0xBF, свободные в списке на packets.html.
14. **Клиент.** `FacingIntent` из мыши: 16 секторов с гистерезисом, только в боевой стойке и только когда курсор над миром. Пакет уходит при смене сектора, не чаще 20 раз в секунду. Своё направление применяется локально сразу.
15. **Совместимость.** Сценарий `walk-route` проходит в обоих режимах с одинаковыми позициями, ClassicUO на том же сервере ходит как раньше.
16. **Сценарий `strafe-test`.** Два бота: первый идёт по прямой и вращает направление тела, второй видит его позицию и `Facing`.

### Критерии готовности

| Проверка | Порог |
| --- | --- |
| Физика против дампа сервера | 100 000 случайных проверок, 100% совпадений |
| Ходьба и бег | 10 000 шагов без отказов при задержке сети до 100 мс |
| Темп | Бег пешком 5 шагов в секунду, верхом 10 (допуск 5%); при включённом `speedhack_detection` сервер не фиксирует подозрений |
| Откаты | После принудительного отказа клиент откатывается и продолжает, очередь не зависает |
| Телепорт, смена карты, толчок 0x97 во время ходьбы | Очередь сбрасывается, следующие шаги принимаются |
| 3б: направление тела | Сосед видит `Facing` не позже чем через 2×RTT, частота пакетов в пределах лимита |
| Совместимость | ClassicUO ходит как раньше, `walk-route` даёт те же позиции в 3а и 3б |
| Unity | WASD, бег и Shift работают, оверлей показывает очередь и отказы |

### Риски

- Расхождение физики клиента и сервера даёт «резиновые» откаты. Их ловит только массовая parity-проверка, поэтому в неё входят динамические препятствия (двери, мобы на клетке).
- Сервер оценивает темп по скользящему окну: подозрение при превышении на 5%, взлом при 10% (`movementThrottle.*`). Клиент, который шлёт шаги чуть быстрее задержки, будет выглядеть читером, поэтому темп проверяется тестом, а не на глаз.
- Для тестов усталости и перегруза нужны GM-команды (стамина, вес), иначе отказы выглядят случайными.
- 3б меняет правила сервера для части сессий. Любая механика, которая читает `Mobile.Direction` (кастер, AI), должна явно решать, ей нужно направление движения или направление тела.

## 6. Стадия 4: базовый геймплей и бой (2–3 недели)

Стадия 4 даёт боту и клиенту всё, чтобы жить в мире: говорить и слушать, видеть своё состояние и навыки, выбирать цели, драться, умирать и воскресать. Здесь же сервер получает правила направления тела для замаха и блока щитом (режим 3б). Подключаются файлы Cliloc, speech.mul, skills.mul и skillgrp.mul.

### Принципы

- Текст (журнал, надписи над головой, тултипы) хранится в Core как данные, а не как отрисовка.
- Тайминги боя и действий принадлежат серверу (`actionDelay`: 1000 мс для AOS и новее, 500 мс раньше; `melee.enableInstaHit`). Клиент их не имитирует, а показывает результат.
- Правила facing включаются серверным флагом и параметрами в конфиге, а не константами в коде.

### Задачи

1. **Текстовые данные.** Cliloc (язык из handshake, аргументы через табуляцию, вложенные ссылки `#id`), speech.mul (ID ключевых слов), skills.mul и skillgrp.mul. *Тест:* для 1000 случайных ID текст с подстановкой аргументов совпадает с тем, что выдаёт сервер (дамп).
2. **Речь: приём.** Пакеты 0xAE (Unicode), 0x1C (ASCII), 0xC1 (Cliloc) и 0xCC (Cliloc с аффиксом). Сообщения попадают в `Journal` по каналам: Regular, System, Emote, Label, Focus, Whisper, Yell, Spell, Guild, Alliance, Command (номера типов в справочнике пакетов). *Тест:* эталонные логи.
3. **Речь: отправка.** 0xAD (Unicode, язык из handshake) с закодированными ключевыми словами (тип с битами 0xC0, до 50 двенадцатибитных ID из speech.mul, схема упаковки в справочнике), запасной вариант 0x03. Команды начинаются с префикса `[` (`commandsystem.prefix`). Лимит сервера для игроков 25 мс на пакет. *Тест:* NPC-вендор реагирует на ключевое слово, GM-команды исполняются.
4. **Состояние моба.** 0x11 (статус, версия по `TARGET.md`), быстрые обновления 0xA1, 0xA2, 0xA3 и 0x2D, замки статов и признак привязанного питомца (0xBF 0x19), запросы статуса и навыков чужого моба (0x34, типы 4 и 5), закрытие статус-окна (0xBF 0x0C). Флаги состояния (яд, паралич, скрыт, боевая стойка, полёт, пол) и известность хранятся в модели. *Тест:* совпадение с серверным дампом `[DumpMobile serial`.
5. **Навыки.** 0x3A (значение, базовое значение, замок, кап), смена замка навыка (0x3A от клиента: индекс и Up, Down или Locked), замки статов (0xBF 0x1A), группировка по skillgrp. Использование навыка идёт пакетом 0x12 с типом команды 0x24 (текст с ID навыка). *Тест:* бот использует навык, сервер отвечает ожидаемым сообщением.
6. **Таргетинг.** Сервер открывает курсор пакетом 0x6C, клиент отвечает 0x6C (19 байт): тип (объект или координаты), ID курсора, флаги (Neutral, Harmful, Beneficial, Cancel), serial, x, y, z, graphic. Отмена передаётся как x и y, равные −1. Быстрые варианты без курсора: 0xBF 0x2C (бинт), 0x2D (заклинание), 0x2E (навык), 0x30 (по ресурсу). *Тест:* бинт на себя, отмена прицела не оставляет висящий курсор.
7. **Боевая стойка и атака.** 0x72 (стойка: флаг и три байта отступа), 0x05 (запрос атаки: serial), 0xAA (текущая цель авто-атаки). *Тест:* бот включает стойку, бьёт моба, получает и наносит урон.
8. **Боевые события.** Анимации (0x6E, 0xE2), урон (0x0B и 0xBF 0x22 для старых клиентов), замах (0x2F). Всё пишется в `CombatLog` как данные. Точный состав исходящих пакетов сверьте по справочнику и эталонному логу.
9. **Смерть и воскрешение.** Анимация смерти (0xAF), статус смерти (0x2C, ответ клиента сервер игнорирует), труп (предмет 0x2006) и его экипировка (0x89), режим призрака у своего моба, воскрешение через серверное окно. *Тест:* GM убивает и воскрешает бота.
10. **Facing в бою (правки сервера).** (а) Замах: если угол между `Facing` атакующего и направлением на цель выходит за дугу (по умолчанию ±1 из 8 направлений, около 135°), замах не засчитывается и не сбрасывает таймер, проверка повторяется примерно через 100 мс. (б) Блок щитом срабатывает, только если защищающийся смотрит на атакующего в пределах дуги, атака сзади его обходит. (в) Лаг: сервер берёт `Facing` на момент замаха с допуском по короткой истории (150–250 мс). (г) Дуги, интервал повтора и окно истории лежат в конфиге, включение идёт флагом. Проверьте, что AI NPC разворачивает тело к цели и пишет `Facing`. Названия методов замаха и расчёта парирования сверьте по исходникам.
11. **Сценарии бота.** `combat-basic`, `death-res`, `facing-melee` (два бота: удар проходит в дуге и не проходит вне её), `facing-shield` (при заданном навыке парирования блок срабатывает спереди и не срабатывает сзади на серии из 1000 ударов).
12. **Unity.** Лента журнала, статус как текст, окно навыков, индикаторы стойки и режима бега, лента боя.

### Критерии готовности

| Проверка | Порог |
| --- | --- |
| Речь | NPC-вендор реагирует на ключевое слово, GM-команды исполняются |
| Состояние мобов | HP, мана, стамина, флаги и статус чужих мобов совпадают с дампом сервера |
| Навыки | Значения, замки и кап совпадают с дампом, использование навыка даёт ожидаемый ответ |
| Таргетинг | Все четыре способа выбора цели работают, отмена не оставляет курсор |
| Бой | Бот убивает моба, умирает и воскресает, журнал боя совпадает с серверным |
| Facing | Замах вне дуги не засчитывается, в дуге засчитывается, после подворота проходит; блок щитом работает только спереди; при RTT 100 мс ложных промахов не больше 1% |
| Лимиты | Скриптовая речь и использование навыков идут без дропов в пределах throttles |
| Unity | Можно говорить, бить, лечиться и смотреть навыки в текстовом интерфейсе |

### Риски

- Для игроков сервер молча отбрасывает пакеты быстрее лимита, поэтому клиент обязан сам выдерживать темп речи и действий.
- Правила facing завязаны на задержку сети: без допуска по дуге и короткой истории направлений игроки будут терять удары из-за лага.
- Версия статуса 0x11 зависит от эры сервера, ошибка проявляется только на реальных данных.

## 7. Стадия 5: предметы, контейнеры, экипировка (2 недели)

Стадия 5 даёт клиенту все действия с предметами: поднять, положить, надеть, открыть контейнер, использовать, прочитать тултип, сесть на маунта. Проверяются не только удачные случаи, но и отказы сервера: перегруз, дальность, запертый контейнер.

### Принципы

- Предмет всегда находится в одном месте: в мире, в контейнере или на слое моба. Перенос между ними — одна транзакция с откатом, если сервер ответил отказом.
- Используем режим сетки контейнеров (байт позиции в сетке в пакете 0x08 для клиентов 6.0.1.7 и новее), поэтому координаты внутри контейнера по containers.cfg не нужны.
- Если `opl.enable` включён (AOS и новее), свойства предметов запрашиваются пакетами, иначе работает одиночный клик (0x09).
- Пакеты 0xEC и 0xED (макросы переодевания) относятся только к Enhanced Client, их не реализуем.

### Задачи

1. **Модель переноса.** `HeldItem` (serial, количество, откуда взят) и состояния «пусто → поднято → положено или отклонено». Запросы: 0x07 (serial, количество), 0x08 (x, y, z, позиция в сетке, serial цели или 0xFFFFFFFF для мира), 0x13 (предмет, слой, моб). Ответы: 0x27 (отказ, откат), эффект полёта 0x23, подтверждения по справочнику исходящих. *Тест:* сценарии мир↔контейнер↔слой, при отказе предмет возвращается на место.
2. **Разделение стопки.** При количестве больше 1 клиент спрашивает, сколько поднять (в отладочном интерфейсе поле ввода).
3. **Контейнеры.** Открытие 0x24 (serial и gump id; gump 0xFFFF означает книгу заклинаний), содержимое 0x3C, добавление 0x25 (с позицией в сетке), удаление 0x1D. Закрытие по расстоянию определите по эталонным логам. *Тест:* содержимое рюкзака и банка совпадает с дампом `[DumpContainer serial`.
4. **Экипировка.** 0x2E (предмет надет), списки экипировки в 0x78 или 0xD3, проверка занятости слоя. *Тест:* надеть и снять предметы на всех слоях, состояние совпадает с сервером.
5. **Использование.** 0x06 (двойной клик; старший бит serial открывает куклу), 0x09 (одиночный), 0xB6 (запрос справки по объекту, язык из handshake). *Тест:* `door-test` из Стадии 3: открытая дверь пропускает, закрытая нет.
6. **Тултипы OPL.** Хэш ревизии (0xDC), запросы 0xBF 0x10 (один предмет) и 0xD6 (пачка), ответ с Cliloc-ID и аргументами, кэш по ревизии, сборка текста через Cliloc. *Тест:* тултипы 100 предметов совпадают с дампом `[DumpProps serial`.
7. **Маунты.** Двойной клик по маунту, предмет на слое 0x19, спешивание двойным кликом по себе, влияние на скорость шага (Стадия 3). *Тест:* после посадки задержка шага меняется на 100 мс (бег) и 200 мс (ходьба).
8. **Покраска.** Окно выбора цвета (0x95) и ответ клиента: serial, неиспользуемый item id, hue с маской 0x3FFF.
9. **Вес и перегруз.** Вес и лимит берём из статуса, отказы при перегрузе разбираем как ответы сервера (`stamina.*`).
10. **Сценарии бота.** `item-lift-drop`, `stack-split-merge`, `reject-cases` (тяжело, далеко, заперто), `door-test`, `mount-test`, `props-parity`.
11. **Unity.** Отладочные окна рюкзака, банка и куклы текстом, перенос кликами.

### Критерии готовности

| Проверка | Порог |
| --- | --- |
| Перенос предметов | Все 3 пары (мир, контейнер, слой) в обе стороны без расхождений с сервером |
| Отказы | Каждый тип отказа даёт откат и сообщение, предмет не теряется и не дублируется |
| Контейнеры | Содержимое и позиции в сетке совпадают с дампом сервера |
| Тултипы | 100 предметов совпадают с дампом, кэш по ревизии не запрашивает повторно |
| Маунты | Посадка, спешивание, смена скорости работают |
| Unity | Можно открыть рюкзак, надеть оружие, положить предмет в банк |

### Риски

- Рассинхрон между клиентским представлением предмета и сервером даёт дубликаты или потерянные предметы, поэтому тесты проверяют инварианты, а не только отдельные пакеты.
- Для pre-AOS серверов тултипов нет, клиент должен корректно работать через одиночный клик.
- Версия клиента определяет формат пакета 0x08 (с позицией в сетке или без), ошибка проявляется как неверное место предмета в контейнере.

## 8. Стадия 6: гампы, диалоги, книги, карты (3 недели)

Стадия 6 даёт клиенту разбор и ответ на все серверные окна: гампы (основной интерфейс ModernUO: крафт, банк, гильдии, админ-инструменты), меню, запросы ввода, книги, карты и доски объявлений. Рендер простой и текстовый, важны корректная модель и правильный ответ серверу.

### Принципы

- Гамп — это данные: `GumpModel` (serial, gump id, позиция, страницы, контролы, строки) отделён от отрисовки, а ответ считается только по модели.
- Состояние ввода (текст, радиокнопки, флажки) хранится в модели и уходит в ответ.
- Не реализуем то, что сервер не использует: пакетов 0xAB и 0xAC (String Query) нет в списке пакетов ModernUO.

### Задачи

1. **Парсер гампов.** Пакеты 0xB0 и 0xDD (zlib: разметка и строки). Команды: page, group, resizepic, gumppic (с hue и классом), gumppictiled, checkertrans, text, croppedtext, htmlgump, xmfhtmlgump, xmfhtmlgumpcolor, xmfhtmltok, button, buttontileart, radio, checkbox, textentry, textentrylimited, tilepic, tilepichue, tooltip, itemproperty, mastergump, picinpic, флаги noclose, nodispose, nomove, noresize. Неизвестная команда даёт предупреждение и пропуск, а не падение.
2. **Ответ 0xB1.** Serial, gump id, id кнопки (0 означает закрытие без кнопки), число и список включённых switch, текстовые поля (id, длина в символах, UTF-16BE). *Тест:* разбор, сериализация и сравнение с оригиналом.
3. **Управление окнами.** Закрытие сервером (0xBF 0x04), повторная отправка гампа с теми же serial и id заменяет окно (сверьте по эталону), флаги запрета закрытия и перемещения учитываются.
4. **Меню выбора.** 0x7C от сервера, ответ 0x7D (13 байт: serial, неиспользуемый id меню, индекс с 1, 0 означает отмену, item id, hue).
5. **Запросы ввода.** 0x9A (ASCII) и 0xC2 (Unicode), ответ тем же типом: serial, id запроса, тип (0 означает отмену), текст. В ответе 0xC2 строка идёт в UTF-16 LE с нулём в конце, в отличие от большинства остальных строк (уточните по эталону). Esc отправляет отмену.
6. **Книги.** Заголовок 0x93 или 0xD4 (UTF-8, название до 60 символов, автор до 30), страницы 0x66 (UTF-8, нумерация с 1, до 8 строк по 80 символов), режимы чтения и записи.
7. **Карты.** Детали карты (0x90, 0xF5) и булавки 0x56 (добавить, вставить, изменить, удалить, очистить, переключить редактирование). Рендер MultiMap.rle отложен до Стадии 9.
8. **Доски объявлений.** 0x71: запрос заголовка (0x04), содержимого (0x03), публикация (0x05), удаление (0x06); учитываются задержки `bulletinboards.*`.
9. **Профиль и подсказки.** 0xB8 (показать или изменить), 0x9B (запрос помощи, 258 байт), 0xA7 и 0xA6 (окно подсказок).
10. **Маджонг (0xDA).** В исходной спецификации его нет, в ModernUO есть (приоритет P3): модель стола и команды ходов и бросков.
11. **Тестовый корпус гампов.** Серверная команда `[DumpGumps` создаёт стандартные гампы (админ, свойства, крафт, банк, гильдия) и пишет сырую разметку. Клиент разбирает, сериализует обратно и сравнивает. Затем бот нажимает кнопки и проверяет эффект (например, открывается банк).
12. **Unity.** Универсальный рендер гампа прямоугольниками и текстом, клик по кнопке отправляет 0xB1.

### Критерии готовности

| Проверка | Порог |
| --- | --- |
| Корпус гампов | 100% разметок разбирается и сериализуется без потерь |
| Ответы | Кнопки, switch и текстовые поля в 0xB1 совпадают с ожидаемыми для 20 типовых гампов |
| Диалоги и запросы | 0x7D, 0x9A и 0xC2 корректно обрабатывают выбор, ввод и отмену |
| Книги | Чтение и правка 10-страничной книги совпадают с сервером |
| Карты и доски | Булавки и сообщения создаются, правятся и удаляются |
| Unity | Открываются админ-гамп, банк и крафт-окно, кнопки работают |

### Риски

- Строки в гампах бывают в Cliloc (xmfhtml), в HTML-разметке и в Unicode, ошибка кодировки проявляется только на отдельных гампах.
- Разные пакеты используют разные кодировки (UTF-8, UTF-16BE, UTF-16LE): ошибка в одной не ловится тестами другой.
- Крупные гампы (списки в сотни строк) должны разбираться без заметных задержек, иначе подвиснет главный поток.

## 9. Стадия 7: социальное, экономика, магия (3–4 недели)

Стадия 7 даёт клиенту взаимодействие с другими игроками и NPC: контекстные меню, торговлю, обмен, группу, баффы, заклинания, боевые приёмы и питомцев. Бо́льшая часть окон приходит гампами из Стадии 6, здесь добавляются собственные пакеты и клиентские макросы.

### Принципы

- Экономика и социальные функции управляются серверными флагами (`vendor_purchase`, `vendor_sell`, `player_vendors`, `player_trading`, `pvp_combat`, `bank_access`). Клиент читает результат, а не дублирует правила.
- Баффы показываются, только если сервер их включил (`buffIcons.enable`).
- Все быстрые действия клиента (макросы, горячие клавиши) подчиняются лимитам `actionDelay` и throttles.

### Задачи

1. **Контекстные меню.** Запрос 0xBF 0x13, показ 0xBF 0x14 (версии 1 и 2), ответ 0xBF 0x15 (serial и индекс пункта). *Тест:* меню питомца и меню вендора.
2. **Вендоры.** Список покупки 0x74 (цены, названия; предметы приходят в слоях 0x1A–0x1C и пакете 0x3C), ответ 0x3B (флаг: 0 — покупка, 2 — отмена; список слой, serial, количество). Продажа: список 0x9E, ответ 0x9F (serial вендора, число предметов, пары serial и количество). *Тест:* купить и продать по одному предмету, баланс золота совпадает с сервером.
3. **Безопасная торговля 0x6F.** Окно с двумя виртуальными контейнерами, синхронизация галочек. От клиента: отмена (1), подтверждение (2), золото и платина (3). Настройки `accountGold.*` влияют на отображение денег.
4. **Группа.** 0xBF 0x06: добавить (1), удалить (2), личное сообщение (3), общее (4), право лута (6), принять (8), отклонить (9). Приглашения, список участников. Пакет с позициями сопартийцев определите по эталонному логу. Квестовая стрелка 0xBA и клик по ней 0xBF 0x07.
5. **Баффы.** 0xDF с таймерами и описаниями через Cliloc.
6. **Магия.** Книги заклинаний (0x24 с gump 0xFFFF, содержимое 0xBF 0x1B, смещения школ 1, 101, 201, 401, 501, 601, 678, 701). Каст: 0xBF 0x1C (флаг книги, serial книги, ID заклинания плюс 1), старые пути 0x12 с типами 0x27, 0x43, 0x56, каст с предварительной целью 0xBF 0x2D. *Тест:* бот кастует по одному заклинанию из каждой школы (GM выдаёт книги и навыки командами).
7. **Боевые приёмы.** Выбор приёма 0xD7 0x19 (индекс, 0 означает сброс), ответы сервера 0xBF 0x21 и 0xBF 0x25 (значок приёма). Для pre-AOS серверов обезоруживание и оглушение (0xBF 0x09 и 0x0A).
8. **Питомцы и расы.** Переименование 0x75 (35 байт, лимит 500 мс), запрос имён 0x98, переключение полёта гаргулий 0xBF 0x32, ответ на смену расы 0xBF 0x2A. Команды питомцам идут речью (Стадия 4).
9. **Гильдия и квесты.** Кнопки куклы 0xD7 0x28 и 0xD7 0x32 открывают гампы, дальше работает Стадия 6.
10. **Клиентские макросы.** LastTarget, LastObject, TargetSelf, очередь WaitForTarget, перебор целей (Next и Prev), подчинение лимитам `actionDelay`.
11. **Сценарии бота.** `vendor-buy-sell`, `trade-two-bots`, `party-two-bots`, `spell-all-schools`, `weapon-abilities`, `pet-commands`, `macro-targets`.
12. **Unity.** Текстовые окна торговли, группы, книги заклинаний, список баффов, кнопки макросов.

### Критерии готовности

| Проверка | Порог |
| --- | --- |
| Вендоры | Покупка и продажа, баланс золота совпадает с сервером |
| Обмен | Два бота обмениваются предметами и золотом, отмена возвращает всё |
| Группа | Приглашение, чат, право лута, выход работают у двух ботов |
| Магия | Каст по одному заклинанию из каждой школы, ошибки сервера (мана, цель) отображаются |
| Боевые приёмы | Выбор и сброс приёма совпадает с серверным значком |
| Макросы | LastTarget, TargetSelf, WaitForTarget работают без нарушения лимитов |
| Unity | Можно купить предмет, обменяться, вступить в группу, скастовать заклинание |

### Риски

- Торговля и золото чувствительны к рассинхрону: любой пропущенный пакет даёт расхождение баланса, поэтому проверяются инварианты.
- Состав пакетов магии и боевых приёмов зависит от эры сервера (AOS, SE, ML, SA): выключенные системы должны не ломать клиент.
- Макросы легко превысить лимиты throttles, поэтому очередь команд клиента должна быть единой и учитывать задержки.

## 10. Стадия 8: дома, кастомизация и корабли (3 недели)

Стадия 8 даёт клиенту составные объекты: размещение домов и лодок, кастомные дома с конструктором и корабли, которые плывут вместе с людьми на палубе. Здесь физика Стадии 3 впервые работает на движущемся multi.

### Принципы

- Мульти состоит из компонентов (Стадия 2), а изменения домов и палубы приходят отдельными пакетами. Клиент не пересчитывает структуру сам, а применяет то, что прислал сервер.
- Размещение домов и лодок управляется флагами `house_placement` и `boat_placement`, распад домов — настройкой `houseDecay.enable`.
- Пакет 0xBF 0x33 (мышиное управление курсом лодки) отсутствует в списке пакетов ModernUO. Лодкой управляют речью, мышиное управление делаем клиентской надстройкой над речевыми командами.

### Задачи

1. **Размещение.** Запрос 0x99 (включая расширенный формат High Seas) и ответ целью 0x6C с координатами. Превью дома или лодки из multi следует за курсором, проверка допустимости остаётся за сервером.
2. **Дома в мире.** Двери, замки и знаки приходят как обычные предметы и гампы (Стадии 5 и 6). Модель дома кэшируется по серийнику.
3. **Кастомные дома: загрузка.** Запрос деталей 0xBF 0x1E (serial фундамента), приём структуры (0xD8, плоскости упакованы zlib, формат в справочнике), ревизии и сброс кэша. *Тест:* структура дома совпадает с серверным дампом.
4. **Конструктор.** Команды 0xD7: backup (0x02), restore (0x03), commit (0x04), delete component (0x05), build (0x06), close tool (0x0C), stairs (0x0D), sync (0x0E), clear floor (0x10), change floor level (0x12, этажи 1–4), roof add и delete (0x13, 0x14), revert (0x1A). Клиентская модель дизайна ведётся по этажам и сверяется с серверной после каждой команды.
5. **Корабли.** Плавное движение 0xF6 (лодка и все сущности на палубе) и пачка пакетов 0xF7. Пассажиры сдвигаются вместе с лодкой без запуска анимации шага. Физика игрока на движущемся multi использует позицию лодки в момент шага. Команды курса идут речью через Стадию 4.
6. **Сценарии бота.** `house-place`, `house-customize-roundtrip` (изменить дизайн и сверить), `boat-place`, `boat-sail` (бот ходит по палубе, пока GM двигает лодку, и каждый тик сверяется с серверным дампом).
7. **Unity.** Отладочный вид дома по этажам, список компонентов, лодка с метками пассажиров.

### Критерии готовности

| Проверка | Порог |
| --- | --- |
| Размещение | Дом и лодка размещаются, недопустимые места отклоняются сервером без зависания клиента |
| Кастомный дом | Структура совпадает с дампом, 20 команд конструктора подряд дают тот же результат, что на сервере |
| Движение по палубе | Бот ходит по палубе плывущей лодки без отказов 0x21 |
| Корабль | Позиции лодки и пассажиров совпадают с серверным дампом на каждом тике 5-минутного плавания |
| Unity | Размещение, вход в дом, смена этажа в конструкторе, плавание работают |

### Риски

- Физика на движущемся multi: небольшая ошибка в позиции лодки даёт постоянные отказы шагов на палубе.
- Формат дома и multi зависит от версии клиента и настройки `maps.enablePostHSMultiComponentFormat`, ошибка проявляется на реальных данных.
- Конструктор дома содержит много состояний (этаж, крыша, лестницы), поэтому без сверки с сервером после каждой команды ошибки накапливаются.

## 12. Сквозные требования

- **CI.** На каждый коммит запускаются тесты Core, фаззинг парсеров и сценарии на фейковом сервере. Ночью запускаются parity-сценарии против реального ModernUO со скриптами-дампами.
- **Обновления ModernUO.** При новой версии сервера матрица пакетов пересобирается из справочника и сравнивается с прошлой: новые пакеты и изменённые поля видны как diff.
- **Диагностика.** Единый логгер пакетов и внутриигровая консоль с счётчиками: неизвестные пакеты, отказы шагов, rtt, объём очередей.
- **Устойчивость.** Любые длины и количества из пакетов проверяются на разумные пределы, неизвестное не роняет клиент, а даёт контролируемый дисконнект с дампом.
- **Производительность.** Разбор пакетов идёт с лимитом времени на кадр, в установившемся режиме без аллокаций.
- **Лицензии и данные.** Файлы данных UO принадлежат EA и у игрока должны быть свои. ModernUO (GPL 3.0) служит справочником, код не копируется. Лицензию ClassicUO проверить по файлу LICENSE при любом порте.

### Оценка сроков (для одного опытного разработчика)

| Стадия | Срок | Зависит от |
| --- | --- | --- |
| 0 Фундамент | 1 неделя | — |
| 1 Сеть и логин | 1–1,5 недели | 0 |
| 2 Данные и мир | 1,5–2 недели | 1 |
| 3 Движение (3а, 3б) | 2–3 недели | 2 |
| 4 Геймплей и бой | 2–3 недели | 3 |
| 5 Предметы | 2 недели | 4 |
| 6 Гампы | 3 недели | 4 (параллельно с 5) |
| 7 Социальное, магия | 3–4 недели | 5, 6 |
| 8 Дома и корабли | 3 недели | 3, 6 |
| Итого Стадии 0–8 | примерно 19–23 недели | без графики |

Это ориентир, а не обязательство: реальный срок зависит от опыта и числа параллельных исполнителей.

## 13. Принятые решения и изменения исходной спецификации

| Решение | Значение |
| --- | --- |
| Версия клиента и эра | Одна, фиксируется в TARGET.md (Стадия 0) |
| Шифрование | Не используется, network.encryptionMode = None |
| Движение | 3а: стандартное, 3б: независимое направление тела по флагу в handshake |
| Управление | WASD, переключатель бега (CapsLock, запасной R), Shift инвертирует режим |
| Направление тела | По мыши, 16 секторов, только в боевой стойке |
| Бой | Замах и блок щитом проверяют направление тела, дуга около 135° по умолчанию, настраивается |
| Архитектура | Core без Unity, сеть в фоновом потоке, главный поток разбирает очередь |
| Исключено из исходной спецификации | Шифрование и 0xE3, 0xF0 и 0xFE (согласование с ассистентами), 0xEC и 0xED (только Enhanced Client), 0x8D (в ModernUO не реализован), 0xAB и 0xAC, 0xBF 0x24, 0xBF 0x12, 0xBF 0x33, сидение на стульях, fastwalk-стек |
| Добавлено к исходной спецификации | Расширение Facing, мини-речь для GM-команд (Стадия 2), серверные дампы для сверки, маджонг 0xDA (P3), runtime-флаги ModernUO (`FeatureFlagManager`), политика лимитов throttles |
| Остаётся с низким приоритетом | Конференц-чат 0xB3 и 0xB5 (по умолчанию выключен: `chat.enabled`), окно подсказок 0xA6, доски объявлений |
